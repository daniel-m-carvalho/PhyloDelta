# Integrating the API

PhyloDelta's server is a JSON HTTP API. Everything the web app does goes through it, so an
integrator (e.g. PHYLOViZ) can upload trees, read comparisons and draw slices exactly as the web app
does. This guide explains the concepts and the main flows with real examples; the complete field-by-
field reference is generated by every running server:

- **`/docs`**: interactive reference (try requests in the browser)
- **`/openapi.json`**: the OpenAPI 3 schema, for generating a client

All endpoints are under **`/api/v1`**. Examples assume `BASE=http://localhost:8000/api/v1`.

## 1. Authentication

The server identifies the caller on every request. Every tree and comparison belongs to an owner,
and a caller sees only their own data plus the shared demo data. The mode is chosen by the
`PHYLODELTA_AUTH` environment variable:

| Mode | How a request is identified | Use |
|---|---|---|
| `mock` (default) | Nothing is checked; every request is one demo user. | Demos and local development. |
| `header` | From the `X-PhyloDelta-Owner: <owner id>` header, trusted as sent. | Testing with several users. **Not security.** |
| `jwt` | From a signed `Authorization: Bearer <token>`. `exp`, `iss` and `aud` are required and checked. | Production, e.g. behind PHYLOViZ's login. |

`jwt` needs:

| Variable | |
|---|---|
| `PHYLODELTA_JWT_ISSUER` | The token issuer (`iss`) to accept. |
| `PHYLODELTA_JWT_AUDIENCE` | This service's audience (`aud`). |
| `PHYLODELTA_JWT_JWKS_URL` | For RS256 tokens from an identity provider (e.g. Google, an institution, PHYLOViZ). |
| or `PHYLODELTA_JWT_SECRET` | For HS256 tokens signed with a shared secret (at least 32 bytes). |
| `PHYLODELTA_JWT_ALGORITHMS` | Accepted algorithms, default `RS256`. Never read from the token. |

The server refuses to start in `jwt` mode with an incomplete configuration. `GET /me` says who the
server thinks you are:

```bash
curl $BASE/me
```
```json
{"owner_id":"local","subject":"local","issuer":"","email":"demo@example.invalid","display_name":"Demo user","mock":true}
```

## 2. Concepts

| Term | Meaning |
|---|---|
| **Tree id** | e.g. `vibrio-upgma` (demo trees) or an opaque id (uploaded trees). |
| **Pair / comparison id** | The two tree ids joined by `__`, e.g. `vibrio-nj__vibrio-upgma`. |
| **Node id** | An integer: the node's position in a pre-order walk of the stored tree. The root is `0`. The same id addresses a node in every endpoint. |
| **Slice** | A part of a tree reduced to at most `budget` tips. Groups that do not fit become **wedges**: one tip standing for a whole clade (`truncated: true`, `true_leaf_count` = how many leaves it hides). |
| **Positional arrays** | Slice nodes come as parallel arrays: entry *k* of every array describes the same node. Comparison values are aligned the same way, so no join is needed. |
| **`null`** | Means "no counterpart / no value", never "zero". Draw it as its own thing. |

## 3. Upload two trees and wait for the comparison

Computing a comparison of large trees takes seconds to minutes, so it happens in the background. The
upload returns at once with an id to poll.

```bash
curl -X POST $BASE/comparisons \
  -F left_tree=@left.nwk \
  -F right_tree=@right.nwk \
  -F left_isolates=@isolates.tsv -F left_isolates_key=ST -F isolates_shared=true \
  -F name="NJ vs UPGMA" \
  -F left_species=vibrio -F right_species=vibrio \
  -F metrics=rf
```

| Field | |
|---|---|
| `left_tree`, `right_tree` | Newick files. **Required.** They must share leaf names. |
| `left_isolates`, `right_isolates` | Optional isolate tables, tab- or comma-separated: a tab in the first line means TSV, otherwise CSV (quoted fields allowed). A header with an empty or repeated column name is refused. |
| `left_isolates_key`, `right_isolates_key` | The column of that table whose values are the tree's leaf names (default `ST`). A column the header does not have is refused at once, with the columns it does have. |
| `isolates_shared` | `true` when `left_isolates` is the table for both trees; send it once. Without it, `left_isolates` alone belongs to the left tree only. |
| `name` | Optional display name. |
| `left_species`, `right_species` | Optional. Declaring them lets the result say whether matching leaf names are the same organisms. |
| `metrics` | Optional, comma-separated metric names (default `rf`). See [Metrics](#9-metrics). |

The response (`202 Accepted`) gives the comparison id and where to poll:

```json
{"id":"<left id>__<right id>","status":"pending","left_id":"…","right_id":"…","poll":"/api/v1/comparisons/<id>/status"}
```

Poll until `status` is `ready` or `failed`:

```bash
curl $BASE/comparisons/$ID/status
```

| Field | |
|---|---|
| `status` | `pending` → `running` → `ready` or `failed`. |
| `ready` | `true` once it can be opened. |
| `error` | Why it failed, when `failed`. |
| `metrics` | The metrics that were asked for. |
| `metrics_ready` | Those that can be read. |
| `metrics_failed` | Metrics asked for that produced nothing, each with its reason. A comparison can be `ready` with entries here: one failing metric does not fail the comparison. |
| `isolates` | Per side (`left`, `right`), how its isolate table met its tree: `key_column`, `rows`, `rows_unmatched` (with up to ten `unmatched_examples`), `rows_without_key`, `leaves`, `leaves_without_rows`. Matching is exact after trimming spaces. A table whose key names no leaf is not used and has `error` saying so; the comparison is still `ready`. |

## 4. List what you have

```bash
curl $BASE/datasets
```

Returns your `trees`, `pairs` (comparisons) and `isolates` (isolate tables). An excerpt:

```json
{
  "pairs": [{
    "id": "vibrio-nj__vibrio-upgma",
    "display_name": "vibrio-nj vs vibrio-upgma",
    "left": "vibrio-nj", "right": "vibrio-upgma",
    "species": "vibrio", "same_species": true, "status": "ready",
    "shared_leaves": 17645, "shared_fraction": 1.0, "caution": null,
    "metrics": ["rf", "rf-treediff"]
  }],
  "trees": [{"id": "clostridium-upgma", "species": "clostridium", "method": "upgma",
             "n_nodes": 55923, "n_leaves": 27962, "max_depth": 604}]
}
```

## 5. Read a comparison

```bash
curl "$BASE/comparisons/vibrio-nj__vibrio-upgma?metric=rf"
```
```json
{
  "pair": "vibrio-nj__vibrio-upgma", "metric": "rf",
  "left": "vibrio-nj", "right": "vibrio-upgma",
  "summary": {"rf": 13650, "rf_normalised": 0.3868, "shared_clusters": 10819,
              "clusters_left": 17644, "clusters_right": 17644, "n_leaves": 17645},
  "shared_leaves": 17645, "dropped_from_left": [], "dropped_from_right": ["211"],
  "same_species": true, "caution": null
}
```

`summary` holds the metric's scores. `dropped_from_*` lists leaves present in only one tree, which
were left out to compare the shared part. `caution` explains why a pair should be read carefully
(e.g. species undeclared or different).

## 6. Draw a tree: slices

The core call. Ask for a tree, or a part of it, reduced to what you can draw. Add `compare` to get
the comparison values for the same nodes in the same response.

```bash
curl "$BASE/trees/vibrio-upgma/slice?budget=4&compare=vibrio-nj__vibrio-upgma&metric=rf"
```
```json
{
  "tree": "vibrio-upgma", "root": 0, "budget": 4,
  "displayed_leaves": 4, "hidden_leaves": 17646, "total_leaves": 17646, "kept": null,
  "nodes": {
    "id":              [0,     17202, 17203, 19865, 17204, 31212, 1],
    "parent":          [-1,    0,     1,     2,     2,     1,     0],
    "label":           ["_",   "_",   "_",   "_",   "_",   "_",   "_"],
    "branch_len":      [null,  0.105, 0.311, 0.724, 5.507, 0.116, 3.615],
    "true_leaf_count": [17646, 9045,  7005,  5674,  1331,  2040,  8601],
    "truncated":       [false, false, false, true,  true,  true,  true]
  },
  "comparison": {
    "id":          [0,    17202, 17203, 19865, 17204, 31212, 1],
    "similarity":  [1.0,  1.0,   0.81,  1.0,   1.0,   0.644, 0.487],
    "corresponds": [0,    11112, 15229, 15229, 11113, 26576, 0],
    "exact":       [true, true,  false, true,  true,  false, false],
    "columns": {}
  }
}
```

| Parameter | |
|---|---|
| `budget` | Maximum tips to return (1–50,000). Size it to the screen: the web app uses about one tip per 14 pixels of panel height. |
| `root` | Node id to start from (default: the tree's root). Use it to open a clade. |
| `compare`, `metric` | Pair id and metric: adds the aligned `comparison` block. |
| `keep` | A node that must be drawn as itself, not folded into a wedge. `kept` in the response says where it ended up: the node itself (`exact: true`), or the wedge holding it (`exact: false`) when the budget is too small to reach it. |
| `around`, `min_leaves` | Instead of `root`/`keep`: show this node *in context*, rooted at its nearest ancestor with at least `min_leaves` leaves (default 20), with the node kept. The chosen root comes back as `root`. One request for a "jump to this leaf". |
| `order` | `size` (default) or `difference`: which clades get the budget first. |

Reading the arrays:

- `parent` is an index into the same arrays (`-1` for the slice root), not a node id.
- A node with `truncated: true` is a wedge; `true_leaf_count` says how many leaves it stands for.
- `similarity` is how well each node matches its best counterpart in the other tree (1.0 = identical
  clade). It is what the web app colours by (divergence = 1 − similarity). `null` means no
  counterpart.
- `corresponds` is that counterpart's node id in the other tree. `exact` is `true` when the
  counterpart has exactly the same leaves.

## 7. Navigate, search and jump

**Open a clade:** request a slice with `root=<node id>`. **Go back:** request the previous root.

**Search by name** (one tree at a time; exact match first, then names that start with the query):

```bash
curl "$BASE/trees/vibrio-upgma/search?q=1203&limit=2"
```
```json
{"tree":"vibrio-upgma","query":"1203","total":11,"exact":1,
 "matches":[{"node":15544,"label":"1203","exact":true,"leaf":true,"leaves":1},
            {"node":32252,"label":"12030","exact":false,"leaf":true,"leaves":1}]}
```

No match is a normal answer (`total: 0`), not an error: "this name is not in this tree".

**Jump to a node with context:** use the slice's `around` (one request):

```bash
curl "$BASE/trees/vibrio-upgma/slice?around=15544&budget=50"
# → "root": 15521, "kept": {"node": 15544, "exact": true, "label": "1203"}, …
```

`GET /trees/{tree}/ancestor?node=&min_leaves=` returns only the ancestor that `around` would choose:

```json
{"node":15521,"leaves":20,"climbed":6,"reached_root":false}
```

## 8. Isolate data

Isolate tables are queried by species (`vibrio`, `clostridium`, or an uploaded table's id).

```bash
curl $BASE/isolates/vibrio/keys                          # the columns, with counts
curl "$BASE/isolates/vibrio/values?key=Source%20Niche"   # a column's values
curl -X POST $BASE/isolates/vibrio/compositions \
  -H 'Content-Type: application/json' \
  -d '{"leaves":["1203","11"],"segment_by":"Source Niche","filter":{}}'
```
```json
{"species":"vibrio","segment_by":"Source Niche","filter":{},
 "leaves":[{"leaf":"1203","total":1,"available":1,"segments":[{"value":"Human","count":1}]},
           {"leaf":"11","total":1,"available":1,"segments":[{"value":null,"count":1}]}]}
```

`compositions` counts, for each leaf, its isolates split by a column, after an optional `filter`
(`{"Country": ["Portugal", "Spain"]}`). `available` is the count before filtering; `available: 0`
means the leaf has no isolate data at all. A segment `value` of `null` means not recorded.

## 9. Metrics

```bash
curl $BASE/metrics
```

Lists the comparison metrics this server can compute: `name` (to pass as `metric`), `title`,
`available` (false when its program is not installed on this server), `version`, the scores it
reports, and `reference`, which says where its implementation comes from:

```json
{"name":"rf","title":"Robinson-Foulds","available":true,"version":"2",
 "reference":{"citation":"PhyloDelta's own implementation, following the method of Branco, A.P.; Vaz, C.; Francisco, A.P. …",
              "doi":"10.3390/a17010015","url":"https://doi.org/10.3390/a17010015"}}
```

## 10. Delete

```bash
curl -X DELETE $BASE/comparisons/$ID
```

Deletes the comparison and the trees and isolate data that only it was using. Data another
comparison still needs is kept. There is no undo.

## 11. Errors

Every error has the same shape, with a stable `code` to branch on and a `hint` saying what to do:

```json
{"detail":"No tree 'nope'.","code":"tree_not_found","hint":"GET /api/v1/datasets lists the trees you have."}
```

| Status | When | Example `code` |
|---|---|---|
| 401 | Missing or invalid credentials | `owner_required`, `token_required`, `token_expired`, `token_invalid` |
| 404 | Unknown tree, comparison, node | `tree_not_found`, `comparison_not_found`, `node_out_of_range` |
| 409 | A stored result was computed by an older metric version and must be recomputed | `metric_version_mismatch` |
| 422 | A parameter is invalid or missing | `invalid_request` (with an `errors` list per field), `metric_not_computed`, `empty_query` |

`detail` may be reworded between versions; `code` will not.

## 12. Limits and deployment settings

| | Default | Setting |
|---|---|---|
| Slice budget | 1–50,000 tips | fixed |
| Search results | up to 200 per request | fixed |
| Upload size | 128 MB per file | `PHYLODELTA_MAX_UPLOAD_BYTES` |
| Allowed browser origins (CORS) | `*` | `PHYLODELTA_CORS_ORIGINS`, set to the frontend's origin in production |
| Data location | `code/server/store` | `PHYLODELTA_STORE` |
| Database | SQLite in the store | `PHYLODELTA_DATABASE_URL`, e.g. a PostgreSQL URL |

Comparisons are computed by the **worker** (`phylodelta worker`), separately from the API. An upload
stays `pending` until a worker is running.
